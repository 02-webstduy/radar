# 用户画像与匹配：第二步设计（本轮不写代码）

> 关键词只能保证"不漏得太离谱"，做不到"懂你"。要让它懂你，得三件事：**画像、分层匹配、进度闭环**。
> 结论先放：**每日链路要确定性（便宜、可评测），Agent 只放在"周度侦察"和"方向生成"上。**

## 0. 一句话

把"关键词匹配"升级成：**画像驱动的召回 → 特征打分 → LLM 只重排 top 10 → 反馈学习**；
再用"每周计划 + 每日动作"给内容加一个 `plan_fit` 维度，最后用证据生成方向卡。

---

## 1. 画像：摘什么、从哪来、多久更新

分两层：**结构化事实**（能查询、能计算）+ **一段自述**（给 LLM 当上下文）。

### 1.1 结构化字段

| 字段 | 例子 | 来源 | 更新 |
|---|---|---|---|
| `goal` | 3 个月内拿到 AI 应用岗 offer | 引导填写 | 季度 |
| `projects[]` | 名字 / 阶段 / 技术栈 / 卡点 / 下个里程碑 | 引导 + 每周 | 每周 |
| `skills[]` | Python 3、RAG 2、评测 1（0 不会 / 3 熟） | 引导 + 反馈 | 每月 |
| `interests[]` | 正向：agent、评测；负向：前端、区块链 | 引导 + 行为 | 持续 |
| `constraints` | 每周 10h、中文优先、偏好工程博客 | 引导 | 季度 |
| `plans[]` | 本周里程碑 / 实验 / 卡点 | 每周三问 | 每周 |
| `actions[]` | 今天做没做那个 30 分钟动作 | 每日勾选 | 每天 |
| `behavior` | save / skip / read / 停留时长 | 页面 | 持续 |

关系：`plans 1—N actions`；`projects 1—N plans`。画像和内容通过**打分函数**关联，不做外键硬绑。

### 1.2 冷启动：7 个问题（5 分钟）

1. 你现在的目标是什么？有截止时间吗？
2. 手头正在做的项目：名字、阶段、现在卡在哪？
3. 你已经会的技术栈（3–6 个）？
4. 你正在学的（1–3 个）？
5. 每周能投入多少小时？
6. 想多看到什么（3 个主题）？不想看到什么（2 个）？
7. 偏好形式：论文 / 工程博客 / 开源项目 / 视频；中文还是英文？

**不要一上来自动挖**：先手填，准；自动抽取（GitHub、笔记）只做补充和纠错。

### 1.3 被动补充（第二阶段）

- GitHub：仓库语言、最近 commit、star 的项目 → 推断"在做什么/在学什么"
- 笔记目录：markdown 标题/标签 → 主题词
- 行为：连续 skip 的主题降权；连续 save 的升权

原则：**每条画像带 `confidence` 和 `source`**，可编辑、可删除；不推断敏感属性。

## 2. 匹配：四层，越往后越贵

```text
候选（5 源，~200 条）
  │  L0 硬过滤：语言 / 时间窗 / 去重 / 拉黑主题
  ▼
  │  L1 召回：BM25（SQLite FTS5）+ 向量 top-k，取并集 ~60 条
  ▼
  │  L2 特征打分：语义 / 词法 / 新近 / 质量 / plan_fit / 技能缺口 / 新颖度
  ▼
  │  L3 LLM 重排：只对 top 10–15 打分 + 写"为什么与你有关"（必须引用画像字段或原文）
  ▼
  │  L4 反馈：save/skip 更新权重；样本够了再上 pairwise 学习排序
  ▼
每天 8 条
```

### 2.1 召回

- **词法**：SQLite 自带 FTS5，建 `items_fts(title, summary)`，直接 BM25，不引额外服务
- **语义**：`bge-small-zh`（本地 CPU，免费）或 API embedding（Jina / OpenAI）
- query 不是一串关键词，而是画像拼出来的一段话：
  `目标 + 当前项目卡点 + 正在学 + 想看的主题`

### 2.2 打分公式（可调，先手工权重）

```text
score = 0.30*semantic + 0.20*lexical + 0.15*plan_fit
      + 0.10*freshness + 0.10*quality + 0.10*skill_gap + 0.05*novelty
      - 0.20*seen_penalty
```

- `plan_fit`：与"本周里程碑/卡点"的语义相似度（这是关键词做不到的）
- `quality`：GitHub stars、HN points、arXiv 分类，归一化
- `novelty`：没推过、且不与已 save 的内容高度相似
- 最后做一次 **MMR** 去重，保证 8 条不全是同一个主题

### 2.3 LLM 重排（只做 top 10–15）

输入：画像摘要 + 本周计划 + 10 条候选；
输出 JSON：`{id, score 1-5, why, tags, difficulty}`，`why` 必须满足：

- 引用画像里的具体字段（"你本周在补 RAG 评测"），或引用原文一句
- 不能写"这是一篇好文章"这种空话

**为什么不让 LLM 每天跑全量**：贵、慢、不稳定、难评测。LLM 只做"最后一公里的判断"。

### 2.4 Agent 放在哪

| 用 Agent | 不用 Agent |
|---|---|
| **周度侦察**：根据技能缺口生成 5 个查询，跨源找"你还没关注的新方向"，给覆盖报告 | 每日抓取：固定源 + 规则更稳 |
| **方向生成**：读进度/收藏/笔记，产出 3 张方向卡 | 每日排序：LLM 分数不稳定，难 A/B |
| 找新源：发现值得加的 RSS/榜单 | 去重、清洗：规则更快更准 |

一句话：**Agent 负责"探索"，管线负责"每天交付"。**

## 3. 把计划和进度纳入评估

### 3.1 数据从哪来

- 每周三问（30 秒）：本周里程碑 / 想验证的实验 / 卡点
- 每日一个动作（10 秒）：今天做没做那个 30 分钟动作
- GitHub：commit / issue 活动（有 token 就能拉）
- 笔记：markdown 目录里本周改动

### 3.2 内容怎么和进度挂钩

每条内容多打三个标签（规则 + LLM 各一半）：

- `unblock`：能解决当前卡点
- `evidence`：能作为项目/简历的证据
- `skill_gap`：补你正在学但还不熟的部分

排序时 `plan_fit` 加权；页面显示"能帮你解决 X"，而不是只显示摘要。

### 3.3 方向卡（每周一次）

输入：本周计划完成情况 + 动作记录 + 收藏内容 + commit + 笔记。
输出 3 张卡，每张必须有：

1. 一句结论（方向）
2. 3 条证据（内容链接 / commit / 笔记）
3. 一个 7 天能验证的实验
4. 止损条件（什么情况下放弃）
5. 需要的资源（数据、文档、人）

**没有证据就不出卡**——这是防"正确的废话"的唯一办法。

## 4. 怎么证明它变好了

| 层 | 指标 | 怎么测 |
|---|---|---|
| 召回/排序 | nDCG@10、P@5 | 你盲标 40 条（相关/不相关），对比关键词 vs 混合 vs +LLM |
| 解释 | 引用覆盖率 100% | 抽 20 条 `why`，检查是否引用了画像字段或原文 |
| 使用 | 打开率、保存率 | 页面埋点 |
| 闭环 | 行动率、周计划完成率 | 每周勾选 |
| 偏好 | 盲选胜率 ≥60% | 新旧排序各 10 条，盲选 20 对 |

没有这组数字，"匹配更好了"只是感觉。

## 5. 两周计划（确认后开工）

### 第 1 周：画像 + 召回

| 天 | 做什么 | 验收 |
|---|---|---|
| 1–2 | 画像表 + 7 问引导（网页表单）+ 导出 `profile.md` | 5 分钟填完，能改能删 |
| 3–4 | FTS5 词法召回 + 向量召回（本地 bge-small 或 API）+ 特征打分 | 每天 8 条，延迟 < 3s |
| 5 | 40 条盲标 + nDCG 基线 + 错误分析 | 有数字、有失败案例 |

### 第 2 周：重排 + 进度

| 天 | 做什么 | 验收 |
|---|---|---|
| 1–2 | LLM 重排 top 10 + `why` + 收藏/跳过按钮 | why 可追溯；反馈落库 |
| 3–4 | 每周三问 + 每日动作 + 方向卡 v0 | 一页能填完；卡片带 3 条证据 |
| 5 | 评测 + README/博客 | nDCG 提升 ≥15%，行动率能算 |

**先不做**：多角色、网站美化、邮件推送、自动抓笔记。

---

## 6. 需要你定的四件事

1. **向量模型**：本地 `bge-small-zh`（免费/隐私/CPU 慢一点）还是 API（省事/按量付费）？
2. **画像入口**：先做网页表单（推荐，之后就是网站的一页）还是 CLI？
3. **方向卡**：只给"建议 + 7 天验证"（推荐），还是直接生成周计划？
4. **隐私**：画像和笔记只存本地 SQLite（推荐），还是允许上传到模型 API 做分析？

## 7. 一个判断

这一步真正的难点不是算法，是**画像的准确性**和**评测的诚实**。
画像错了，再好的排序也是错的方向；没有盲标，再复杂的模型也只是自嗨。
所以顺序是：**先画像 → 再召回 → 再重排 → 最后才上 Agent**。

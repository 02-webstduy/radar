# 进度追踪：接入口、准确性、第一版设计

> 画像回答"你是谁"；进度回答"你在往哪走、走了多远、卡在哪"。
> 关键判断：**活动 ≠ 进度**。提交多、笔记多，不代表离目标更近。

## 0. 先把"进度"定义清楚

一条可追踪的进度，至少要有四段：

```text
目标（goal） → 里程碑（milestone） → 下一步动作（action） → 证据（evidence）
```

- **目标**：3 个月内拿到 AI 应用岗
- **里程碑**：radar 有 20 条真实标注 + 一次盲测
- **动作**：这周把标注按钮和 nDCG 跑通
- **证据**：commit / PR / 截图 / 测试输出 / 笔记链接

没有证据的"我做了"，只能算**声称**，不能算**完成**。这是准确性的根。

## 1. 接入口全景

| 接入口 | 能拿到什么 | 准确性 | 成本 | 隐私 | 建议 |
|---|---|---|---|---|---|
| 每周三问（自报） | 本周做了什么 / 卡在哪 / 下周做什么 | 意图强、频率低、会美化 | 低 | 低 | **必做**，作为对账基准 |
| 每日一句 | 今天那一个 30 分钟动作 | 高意图、易断更 | 极低 | 低 | 推荐，替代长日记 |
| GitHub / GitLab / Gitee | commit、PR、issue、release、文件变更 | 客观但嘈杂（改文档也算） | 中（token） | 中 | **第一批** |
| 笔记（Obsidian/Logseq/md） | 标题、todo、修改时间、总结 | 意图强、格式不统一 | 低 | 中 | **第一批** |
| 任务管理（Todoist/滴答/Vikunja） | 计划、完成率、逾期 | 高（计划 vs 实际） | 中（API） | 中 | 第二批 |
| 日历（Google/飞书/ICS） | 学习/项目时间块、会议 | 时间准，产出不准 | 低 | 中 | 第二批 |
| WakaTime / VS Code | 按项目/语言的编码时长 | 工时准，产出不准 | 低 | 中 | 可选 |
| Zotero / Readwise / 高亮 | 读了什么、标了什么 | 学习输入准，吸收不准 | 中 | 中 | 科研向再加 |
| 课程平台（Coursera/B站/极客时间） | 课程进度、证书 | 完成度准，掌握度不准 | 中 | 低 | 可选 |
| 求职记录（投递/面试） | 投了多少、到第几面 | 与目标直接相关 | 手动/邮件解析 | 高 | 求职期很值 |
| CI / 测试结果 | 测试通过、覆盖率、构建 | 很客观 | 低 | 低 | 项目健康度 |
| 语音/快速记录 | 30 秒口述今天 | 低摩擦 | 低 | 中 | 以后 |
| 屏幕时间/微信/QQ | 使用时长、聊天 | 侵入、合规风险 | 高 | 极高 | **不做** |

**结论**：先做"自报 + 两类客观信号（GitHub、笔记）"，再用"任务/日历"补计划与时间；其余按目标相关性加。

## 2. 准确性：四道校验，而不是一个分数

### 2.1 证据门槛

- 动作标"完成"时，必须挂一个证据（URL / commit / 测试输出 / 截图）
- 没证据 → 状态是「声称完成」，不计入里程碑
- 证据可以很轻：一条 commit、一段笔记、一个链接

### 2.2 交叉验证

同一件事从三个角度看：

| 角度 | 来源 | 冲突时怎么办 |
|---|---|---|
| 你说做了什么 | 每周三问 / 每日一句 | 以证据为准，让你确认 |
| 系统看到什么 | GitHub / 笔记 / CI | 可能漏（私有仓库、没写笔记） |
| 你花了多少时间 | 日历 / WakaTime | 只做参考，不参与"完成"判定 |

冲突例：你说"做完了数据源"，但 GitHub 没有对应 commit、笔记也没写 → 标「待验证」，下周对账时问一句。

### 2.3 周对账（最关键的一步）

每周 10 分钟：

1. 列出本周所有信号（commit、笔记、完成任务）
2. 让系统猜它对应哪个里程碑
3. 你确认 / 改绑 / 忽略
4. 没证据的声称 → 标「未验证」
5. 更新下周三个承诺

**准确度不靠模型猜，靠这次人工对账。** 模型只负责把信号整理好、把问题问对。

### 2.4 指标：分开看，不合成一个"进度分"

| 指标 | 算法 | 说明 |
|---|---|---|
| 计划完成率 | 完成动作 / 计划动作 | 看你是否说到做到 |
| 证据覆盖率 | 有证据的完成 / 声称完成 | 看进度有多"实" |
| 阻塞时长 | 卡点持续天数 | 比"忙不忙"更有用 |
| 动量 | 本周有信号的天数 | 防三天打鱼 |
| 目标距离 | 已完成里程碑 / 总里程碑 | 只看里程碑，不看活动 |

一个"进度 72 分"没有意义；五个维度一起看才有判断。

## 3. 数据模型（SQLite）

```sql
goals(id, title, horizon, status, created_at)
milestones(id, goal_id FK, title, due, status, created_at)
actions(id, milestone_id FK, title, planned_for, done_at,
        evidence_url, source, confidence)
signals(id, source, kind, occurred_at, payload JSON,
        confidence, action_id FK NULL)
checkins(id, week, done, blocked, next)
```

- `signals` 是原始事件（commit / 笔记变更 / 任务完成），**不直接算进度**
- `actions` 是人对计划的承诺；`signals.action_id` 建立"证据 → 动作"的关联
- `checkins` 是每周对账的输入，也是下周计划的来源

## 4. 接入口适配器

| 适配器 | 拉什么 | 认证 | 频率 |
|---|---|---|---|
| `github` | 指定 repo 的 commits / PR / issues | 只读 token | 每天 |
| `notes` | 指定目录的 md：mtime、标题、`- [ ]`/`- [x]` | 无 | 每天 |
| `todoist` | 任务与完成时间 | API token | 每天 |
| `calendar` | ICS 事件（只读） | 订阅链接 | 每天 |
| `wakatime` | 按项目时长 | API key | 每天 |

第一批只做 `github` + `notes`，因为：
- 不需要额外账号
- 一个看产出，一个看意图
- 都能落到"证据"

## 5. 第一版切片（约 1 周）

### 页面 `/progress`

- 顶部：本周目标 + 3 个承诺（每周三问）
- 中间：本周信号流（commit / 笔记 / 完成任务），每条可"关联到动作"
- 底部：指标五项 + 下周计划入口

### 后端

1. 建 `goals / milestones / actions / signals / checkins` 五张表
2. `notes` 适配器：扫目录，抓本周修改的 md，提取标题和 todo
3. `github` 适配器：1–3 个 repo 的 commits + PR（只读 token）
4. 周对账接口：未关联信号列表 + 手动绑定
5. 指标计算：计划完成率、证据覆盖率、阻塞时长、动量

### 验收（一周后）

- 能回答：这周做了什么、卡在哪、下周做什么
- 证据覆盖率 ≥ 60%（低于这个，说明"完成"太虚）
- 周对账 10 分钟内完成
- 不要求"自动算出进度百分比"

## 6. 现在不做什么

- 不做屏幕时间/微信/QQ 抓取（侵入、合规风险）
- 不做"工时排行榜"（会激励磨洋工）
- 不做全自动进度百分比（会制造虚假确定性）
- 不接超过 3 个源（先把对账跑顺）

## 7. 需要你定

1. **第一批接入口**：GitHub + 笔记（推荐）/ 再加日历 / 再加 Todoist
2. **GitHub 范围**：只读 token + 哪几个 repo（公开/私有都行）
3. **笔记目录**：你的 md 放在哪个路径（Obsidian/Logseq/普通文件夹）
4. **进度单位**：里程碑 + 证据（推荐）vs 工时/活动量
